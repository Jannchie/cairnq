# CairnQ Protocol v1

CairnQ is a **SQLite-first, cross-language, storage-centered durable task runtime**.
API and worker processes never call each other — they coordinate only through a
shared SQLite database. This document is the canonical contract that the Python
and TypeScript SDKs implement identically.

`protocol_version = 1`

## Source of truth

- **Schema**: `migrations/<dialect>/*.sql` (ordered, idempotent) — currently
  `migrations/sqlite/0001_init.sql`; a Postgres backend adds `migrations/postgres/`.
  There is no separate `schema.sql`; migrations are canonical.
- **State transitions**: `sql/<dialect>/*.sql` (currently `sql/sqlite/*.sql`). One
  statement per file, named (`:param`) parameters. **Both SDKs load and execute
  these exact strings** — this is the primary anti-drift guarantee now that there
  is no DB function layer. A backend selects its subtree by dialect; the
  conformance scenarios below are dialect-neutral and run against each.
- **Behavior**: `conformance/scenarios/*.json` — language-neutral step/assert
  data both SDKs run verbatim.
- **Status set**: the `status` CHECK constraint in `migrations/sqlite/0001_init.sql`
  is the canonical list of states. Each SDK declares it once (deriving its
  `TaskStatus` type from a single runtime constant — `STATUSES`) and a conformance
  check pins that set against the CHECK, so the SQL and both SDKs can't silently
  diverge.

## Conventions

- **Time**: integer epoch milliseconds in `*_ms` columns. The SDK supplies
  `:now_ms` on every call (same-host → one clock). A future Postgres backend
  would switch to DB `now()`; the `TaskStore` abstraction hides this.
- **JSON**: `payload` / `result` / `error` / `metadata` are TEXT validated by
  `json_valid()`. SDKs `JSON.stringify` before binding and parse on read — parsing
  only when the driver returns text (a `jsonb` backend returns already-decoded
  objects). No language-private types cross the boundary (no pickle, no class
  instances, no Buffer). Large blobs go by reference (e.g. `{"image_url": "s3://..."}`).
- **IDs**: generated by the SDK as `task_` + 26-char Crockford base32 ULID
  (48-bit ms timestamp + 80-bit randomness, lexicographically time-sortable).
  This is the only behavior not pinned by shared SQL, so its format is asserted
  by conformance. Top-level tasks have `root_id == id`.
- **Booleans** cross the SQL boundary as `0/1` integers (`retryable`,
  `reset_attempt`); both drivers reject native booleans.

## State machine

```
queued  -> running            (claim)
running -> succeeded           (complete / succeed, no pending cancel)
running -> failed              (fail, terminal)
running -> queued              (fail retryable & attempt<max; or lease recovery)
queued  -> canceled            (cancel)
running -> (cancel_requested)  (cancel; cooperative — worker exits via ctx.canceled())
running -> canceled            (complete, when a cancel was requested — cancel wins)
failed/canceled -> queued      (retry)
```

Terminal statuses: `succeeded`, `failed`, `canceled`.

A worker finalizes a finished handler with **`complete`** (not raw `succeed`): if a
cancel was requested while it ran, the task becomes `canceled` and the result is
discarded; otherwise `succeeded`. This is the only path by which a *running* task
reaches `canceled`. Raw `succeed` is a lower-level primitive that always succeeds
(used in tests / advanced flows).

## Lease model (at-least-once)

A worker **leases** a task rather than popping it:

- `claim` sets `status=running`, `worker_id`, `lease_until_ms = now + lease_ms`,
  and `attempt += 1`. It is atomic: a single `UPDATE … WHERE id IN (SELECT … LIMIT)
  RETURNING *` run inside `BEGIN IMMEDIATE` — the SQLite equivalent of
  `FOR UPDATE SKIP LOCKED`. `busy_timeout` absorbs `SQLITE_BUSY`.
- `heartbeat` extends `lease_until_ms`. All worker writes
  (`heartbeat/progress/succeed/fail`) are **ownership-checked**:
  `status='running' AND worker_id=:worker_id AND lease_until_ms > :now_ms`.
  Zero rows updated ⇒ the lease was lost (expired and reclaimed by another
  worker) ⇒ SDK raises `LostLease` and the zombie worker stops.
- `recover_leases` (run just before `claim`, same transaction) reclaims expired
  running tasks: `attempt < max_attempts` → back to `queued`; else → `failed`
  with a lease-expired error envelope.

> **At-least-once, not exactly-once.** A worker may finish external side effects
> then crash before `succeed`; after lease expiry the task is redelivered. Use
> `task_id` / `key` for idempotency on side effects.

> **Never hold a transaction while executing the task.** claim is its own short
> transaction; the handler runs transaction-free; progress/heartbeat/succeed/fail
> are each their own short write. This keeps SQLite's single-writer limit a non-issue.

## Key conflict (`cairnq_task_keys`)

`key` is a business-stable pointer to the *current* task; `task_id` is one
execution. On `submit` with a `key`, inside `BEGIN IMMEDIATE`:

- `reuse` — key exists → return the existing task.
- `reject` — key exists → raise `AlreadyExists`.
- `replace` — cancel the existing task, insert a new one, repoint the key.

Single-writer + `BEGIN IMMEDIATE` serializes concurrent same-key submits.

> **`reuse` returns the recorded task whatever its state** — including a terminal
> `succeeded`/`failed`/`canceled` one. It is idempotent submit, not "re-run if the
> last attempt failed". To force a new run, use `replace` (new task, repoints key)
> or `retry` (re-enqueue the same task).

## Operations

Client-side (API role): `submit`, `get`, `get_by_key`, `list`, `cancel`,
`cancel_by_key`, `retry`, `retry_by_key`, plus SDK-orchestrated `wait` / `call`.
Worker-side: `claim`, `heartbeat`, `progress`, `complete`, `succeed`, `fail`.

`claim` first runs a read-only `claimable_probe`; only if it reports work does it
open the `BEGIN IMMEDIATE` write transaction (recover expired leases + claim). This
keeps idle workers off SQLite's single write lock.

`wait` and `call` are **SDK-orchestrated polling** over `get` (100–500ms backoff
to terminal/timeout) — the only non-SQL operation, read-only, leaving room to
swap in a smarter wakeup later. `call = submit + wait`; on timeout it raises
`TaskTimeout(task_id=...)` and **the task keeps running**.

Per-statement parameters are documented in the header comment of each
`sql/sqlite/*.sql` file.

## Error envelope

Errors stored in `error` and surfaced by SDKs are JSON, never a language
exception object:

```json
{
  "type": "RateLimitError",
  "code": "rate_limited",
  "message": "model provider rate limited the request",
  "retryable": true,
  "details": { "provider": "openai" }
}
```

SDKs wrap a terminal `failed` task's envelope as `TaskFailed` (Python) /
`TaskFailedError` (TS).

## Concurrency, limits & security

CairnQ targets same-host coordination. Know the edges:

- **One writer at a time.** SQLite (WAL) allows concurrent readers but a single
  writer. `claim` / `submit` / worker writes are short transactions, but under
  many writers they serialize. The `claimable_probe` keeps *idle* workers off the
  write lock; busy workers still contend.
- **A contended write can block synchronously.** The TypeScript SDK uses
  better-sqlite3 (synchronous); on `SQLITE_BUSY` it blocks the thread up to
  `busy_timeout` (default 5s), stalling that process's event loop meanwhile. The
  Python SDK serializes all DB work on one connection behind a lock. Both are fine
  for low-write, long-running AI workloads; neither is a high-throughput MQ.
- **Same host only.** Do not put the database on a network filesystem and do not
  share the file across machines — WAL requires processes on one host. Multi-host
  is a future Postgres backend (designed-for via the `TaskStore` seam).
- **No in-database authorization.** Unlike a Postgres role model, any process that
  can open the SQLite file has full read/write access and executes SQL directly.
  Protect the file with OS permissions; treat DB access as full trust.

## Versioning

`cairnq_meta` holds `protocol_version` and `schema_version`. On startup an SDK
reads `protocol_version` and refuses to run if its supported major differs.

Migrations are applied in filename order and recorded in `cairnq_migrations`
(name primary key); each runs at most once, so future non-idempotent migrations
(e.g. `ALTER`) apply cleanly.
